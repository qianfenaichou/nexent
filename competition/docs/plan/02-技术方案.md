## 1. 知识模型与版本化（K0 + A3）

### 1.1 「知识进化」的形式化

**本体** O = (C, P, R, A, ≤)：C 类集合 / P 属性集合 / R 关系类型集合 / A 公理集合 / ≤ 继承偏序（单继承为主）。

**版本序列** O₀ → O₁ → ... → Oₜ。**演进操作集** Op（每条带操作码）：

| 操作码 | 载荷 | 操作码 | 载荷 |
|---|---|---|---|
| `CLS_ADD/UPD/DEPRECATE/DEL` | class_id, payload | `REL_ADD/UPD/DEPRECATE` | rel_type_id |
| `PROP_ADD/UPD/DEPRECATE` | prop_id（属性不物理删） | `AXIOM_ADD/DEL` | axiom |

**弃用优先于删除（DECISION）**：类/属性/关系一律 `DEPRECATE`（保留历史供图谱旧数据回溯），只有"从未被任何实例引用且提案被否决"的元素才允许 `CLS_DEL`。理由：决策卡的知识版本戳要能回溯旧版本本体，物理删除会打断溯源链（KG 工程 append-don't-rewrite 原则）。

### 1.2 本体 diff 的定义（不做 NP 的图同构）

**DECISION：用"结构化编辑脚本"定义 diff**——因为版本由我们自己生成，操作日志天然可得：

- **主定义（正向）**：版本化时把人工确认的操作持久化为 `ontology_change_proposal_t.applied_ops`（JSONB），`diff(O_t, O_t+1) = 操作日志回放`，成本 O(1)。
- **辅助定义（校验）**：按 `stable_id`（内容无关持久 ID）做集合差，输出 `added/removed/changed` 三桶。`stable_id` 首次创建时分配、跨版本不变，避免"改名被误判为删+增"。
- **输出格式**：`ontology_diff` MCP 工具与前端 diff 视图共用 schema：`{version_pair, ops: [{code, target, before, after, proposal_id, confirmed_by, confirmed_at}]}`。

**图谱增量** ΔG 同理：`kg_extract_run_t` 记录每次抽取的 added/merged/superseded 边，`ΔG = (ΔV, ΔE, ΔA)`（ΔA 是对齐产生的 alias/merge/split）。

### 1.3 本体质量指标（4 个，全部可 SQL 化）

| 指标 | 定义 | 实现 | 目标值 |
|---|---|---|---|
| **覆盖率 Cov** | 文档概念集合中被本体覆盖的比例 | 概念表 JOIN 类名/别名表，一次聚合 | ≥85%（E） |
| **冗余度 Red** | 语义近重复类对占比（sim>0.85 且非祖先） | 预计算类名向量，一次 JOIN | ≤5% |
| **深度分布 Dep** | 继承树深度直方图；Dep_max、Dep_mean | 递归 CTE | Dep_max ≤5，Dep_mean∈[2,3] |
| **标准对齐度 Align** | 锚定到标准文档条目的类占比 | `ontology_class_t` 聚合 | ≥60%（种子来自标准目录） |

**"文档概念集合" ground truth 构造（DECISION：双抽样协议）**：不做大规模标注——每域随机抽 3 组×40 句，2 名队员独立圈概念，合并去重（约 60-90 概念/组）；Krippendorff α ≥0.6 视为指导书有效。单组成本约 1.5 人时。

### 1.4 进化有效度与成本（双指标并列，不做单一比值）

- **Δ质量**：`ΔAcc = Acc(test_set, K_t+1) - Acc(test_set, K_t)`（pp），在固定测试集（版本敏感题加权子集）上；附 ΔTrace。
- **成本**：`Cost_evolve = tokens(检测+对齐+提案+重算) + 人工确认分钟数`；与 `Cost_rebuild`（全量重建估算）对比。
- 实践预期区间 [+5pp, +25pp]（E）。辅助量 `ROI = ΔAcc / Cost_evolve` 仅答辩展示用。token 折算为元，人工时间按 50 元/时（学生机会成本口径，注明估算）。

## 2. L2 知识引擎：本体与图谱构建

### 2.1 本体半自动构建流水线（K1，★含创新点③）

**方案选型（DECISION：种子本体引导）**：

| 维度 | (a) 纯 LLM 自由归纳 | **(b) 种子本体引导（胜出）** | (c) 模式归纳 |
|---|---|---|---|
| 本体质量 | 信噪比低、类目漂移 | 种子锚定标准文档，粒度有参照 | 依赖实例覆盖度 |
| 专家负担 | 高 | **低（确认为主）** | 中 |
| 对齐度 | 低（无锚） | **高（天然锚定标准目录）** | 低 |
| 低资源适应 | 差 | **好（few-shot 种子即先验）** | 差（需标注实例=违背前提） |

**流水线**：
```
【阶段0 种子】标准/指南文档（目录+章节标题+术语表）
   │ S1 目录结构解析 → 层级骨架候选（深度≤3）
   │ S2 术语提名：每章 few-shot 提名 top-K 概念（K=8-12）+ 别名 + 预期父类
【阶段1 概念提名】LLM 两级提案·第一级（中档模型）
   │ 输出：[{name, aliases[], parent_stable_id, evidence_span, confidence, rationale}]
【阶段2 校验】规则校验器（见 §2.2）→ 违规自动修复 or 上报
【阶段3 人工确认·轻交互】提案队列（按 §2.3 排序）→ 确认/否决/改父类
【阶段4 schema 装配】第二级：为已确认类生成属性/关系提案（大档模型）
【阶段5 校验+确认】（同 2-3）
【阶段6 版本化】操作日志持久化 → ontology_version_t 新版本 → 图谱侧影响队列
```

**★创新点③：人审预算优化（重述原"效率对照实验"）**

原设计是"人工基线 vs 半自动"对照实验，但**人工基线由队员扮演专家，方法学上会被击穿**。重述为：

> **在固定专家确认预算下，最大化本体质量**——横轴 = 专家确认次数（预算），纵轴 = 本体质量四指标。这是**文献零命中的空白（A2）**。

实现：提案排序按 **value-of-information** 降序（而非简单加权）：
```
VOI(proposal) = P(提案被确认的概率) × impact(该提案能收编多少 unmappable 实体 + 覆盖多少证据段)
排序目标：专家先看"高影响高置信"；预算耗尽即停止，未确认的提案自动推迟。
```
- 定义 `auto_accept` 线（conf ≥ τ_a 且校验通过 且证据富度=1.0），扫描 τ_a ∈ {0.70...0.95}，记录「人工干预比例 vs 抽检错误率」曲线——**给"每降低 10% 人工干预付出多少质量"一条实证曲线**；
- 生产值取"抽检错误率 ≤3%"的最大自动线。

**多模型交叉**：第一级提名用中档（成本低 5 倍）；schema 装配与审校 pass 用大档。温度 0.2，批量提案（每章一次），层级提案（一次一章，动态注入当前骨架摘要）。

### 2.2 一致性校验器（形式约束 + 语义约束）

| # | 类型 | 规则 | 处置 |
|---|---|---|---|
| V1 | 形式 | 继承无环（DFS 三色） | **自动修复**：拒绝挂载，回提案者重提父类 |
| V2 | 形式 | 单继承（parent 唯一） | 自动（schema 层强制） |
| V3 | 形式 | 属性类型 ∈ {string,float,int,bool,enum[],date,ref} | 自动拒绝违规 |
| V4 | 形式 | 命名规范（类 UpperCamelCase、属性 lower_snake、中文别名单独字段） | 自动规范化 |
| V5 | 形式 | 深度 ≤5 | 自动（挂到第 5 层强制提平级或拒绝） |
| V6 | 语义 | 同义类检测：`sim(emb)>0.85 且非祖先后代` | **上报**：标 duplicate_of，专家裁决 |
| V7 | 语义 | 粒度冲突（"药品"vs"二甲双胍"） | **上报+建议**：LLM 提示层级，专家确认 |
| V8 | 语义 | 孤儿类（无属性/关系/实例） | 自动标记，30 天无引用 → DEPRECATE 提案 |
| V9 | 语义 | 关系 domain/range 与两端类公理相容 | 自动拒绝并回提案 |

自动修复优先于人工上报（V1-V5/V9 机器兜底），语义冲突（V6-V8）才消耗专家时间——**"专家只看真问题"的机制保证**。

### 2.3 图谱抽取（K2，★含漏洞修正）

**★漏洞修正一：本体注入改为子图检索（解 15k 硬编码炸弹）**

原设计：抽取时注入全量本体摘要（硬编码 `ONTOLOGY_SUMMARY_TOKEN_LIMIT=15000`），超限则截断——**本体一长大就被截断，越靠后的文档抽取质量越差**。

修正：**本体子图检索（Ontology RAG）**
- 为每个类/属性/关系建 embedding 索引；
- 抽取某 evidence span 时，先检索**与该 span 最相关的本体子图**（top-k 类 + 父类链 + 相关关系类型），只注入子图（通常 <3k token）；
- 收益：token 恒定、抽取一致性提升、本体可无限扩展（打破 15k 上限）；**且这本身是一个消融点**（全量注入 vs 子图检索的抽取一致性/成本对比）。

**抽取协议**：
```python
extraction_prompt = {
  "ontology_subgraph": retrieve_ontology_subgraph(chunk, top_k=15),  # ★子图检索
  "evidence_span": chunk.text,
  "fewshot": RETRIEVE_DYNAMIC_EXAMPLES(chunk),  # 静态3例 + 动态2例（从已确认高质量抽取库检索）
  "output_schema": [Entity(type=OntologyClassRef, name, aliases, props, provenance, tag),
                    Rel(src, dst, rel_type, claim, tag)]
}
# tag ∈ {EXTRACTED, INFERRED}
```
- **锚定规则**：抽取的 `type` 必须是本体 active 类的 stable_id/类名；无法映射 → ① LLM 判断是新概念 → 进 `kg_pending_entity_t`（高频者触发 K1 增量提案）；② 是已有类的别名 → 进对齐通道。
- **多模态**：表格走**确定性解析**（列头→属性、行→实体，零 LLM、可复现）；图文走图注锚定（VLM 可选，首版只抽图注文字）；正文走 LLM 通道。

**★漏洞修正二：实体对齐引入外部标识主键**

原设计：`sim > 0.85 自动合并`，并称"二甲双胍=格华止"能直接合并——**算法上不成立**（generic 与 brand 是"同指异名"，embedding 相似度远达不到 0.85；若为合上而降阈值，又会误合并"阿卡波糖"）。

修正为**三段式对齐**：
```
新实体 e（含 aliases）
 └─ 第0级 blocking（★新增）：外部标识主键匹配
      ATC 编码 / 国家医保药品分类与代码 / NMPA 批准文号本位码 / 药品别名表
      命中 → 直接合并（同指锚点，权威）；记 alias_type: brand/generic
 └─ 第1级 向量候选（块内）：sim(emb(e), emb(existing)) 
      s > τ1=0.80 → 自动合并；s ∈ (τ2=0.60, τ1) → 候选带审 → 第2级；s ≤ τ2 → 新建
 └─ 第2级 LLM 裁决：输入 (e 证据段, 候选实体证据段摘要) → merge/split/new + 理由
      置信 ≥0.9 → 执行；否则 → 第3级
 └─ 第3级 人审兜底：待审池 UI（复用本体工作台）
```
- **阈值标定**：T-06 首周人工标注 200 对实体相似度，画 ROC，取"假合并率 ≤2%"为 τ₁、"召回 ≥95%"为 τ₂。
- **错误合并检测与拆分**：信号（属性值矛盾/不同 ATC 编码/证据链同名不同指）；操作 `SPLIT(e, criteria)` → 两个新实体 + 原实体 DEPRECATE + `split_into` 双边；图谱不物理删除，整轮可逆。
- 参考：Splink（PG 后端概率式实体消解，MIT）、Jellyfish（字符串相似度）、DiaKG（糖尿病标注数据集）。

### 2.4 bi-temporal 增量更新（K2）

**双时间戳模型**：每条实体/关系带四字段——`valid_at`/`invalid_at`（事实有效时间轴）+ `retrieved_at`/`superseded_at`（系统认知时间轴）。查询默认取现行视图（`valid_at ≤ now AND (invalid_at IS NULL OR invalid_at > now)`）；决策卡可显式请求历史视图。

**合并冲突解决**：

| 冲突类型 | 规则 | 理由 |
|---|---|---|
| 新增事实 | 直接合并 | — |
| 补充性事实（属性级） | 追加新属性值（带 source） | 属性多值不冲突 |
| **矛盾事实**（关系级） | **时效性优先**：新指南 valid_at 更晚者现行；旧事实 invalid_at 打戳保留 | 医疗"历史建议仍被引用"，且是 Q2 演示素材 |
| 来源权威度 | tie-breaker：同 valid_at 时 authority_level 高者现行 | 版本演进以标准体系为纲 |
| 同源同版本内部矛盾 | 两边保留 + contested=true + 人审 | never silently overwrite |

**DEPRECATE vs 保留带版本戳（DECISION）**：医疗场景**默认"保留带版本戳"**，只有新版显式否定（"不再推荐"）才 invalid_at 失效。理由：①历史用药建议仍有回溯价值；②直接制造 Q2 演示的最强素材；③删除不可逆，打戳可逆。

### 2.5 ★新增子系统：冲突消解（Conflict Reconciliation）

当前设计只有"contested 不自动合并"的**原则**，没有**算法**。但多版本、多来源（指南 vs 说明书）下冲突是常态——这是"可进化"能否成立的工程地基。

**三层算法**：
1. **冲突检测**：同 (src, rel_type, dst) 或同实体同属性、值矛盾、且 valid_at 区间重叠 → 冲突候选；
2. **冲突分类**：真·知识演化（新旧版本）/ 来源差异（权威度）/ 抽取错误 / 同源矛盾（参考 EvoTrustRAG 2608.07933 的归因思想）；
3. **消解策略**：演化型→时效优先+旧事实打戳；来源差异型→按 authority_level 定现行+保留分歧标注；抽取错误型→回抽取队列；同源矛盾型→contested+人审。
   **输出：每条冲突的裁决记录**（可溯源、可回放）——评分维度2"决策链路可溯源"的深层兑现。

### 2.6 存储选型（A1）

| 维度 | **PG JSONB + 递归 CTE（胜出·默认）** | graphiti-core | PG+AGE | Neo4j |
|---|---|---|---|---|
| 新增运维面 | **零** | +1 库/DB | +PG 扩展 | +1 图数据库 |
| 与 Nexent 事务一致性 | **同库同事务** | 跨存储 | 同库 | 跨存储 |
| 多跳（≤3跳,2万节点,E） | 递归 CTE+GIN，p95 200-800ms | 快 | 中 | 最快 |
| bi-temporal 自由度 | **全自定义** | 库内建（语义近但目标不同） | 自定义 | graphiti 内建 |
| 上游同步冲突 | **零** | 零 | 中（PG 版本联动） | 零 |

**DECISION：默认 PG JSONB + 递归 CTE**。理由：①规模（单域 2 万实体/3 万边/深度≤3）在 PG 舒适区；②同库使"决策卡引用图谱证据"可用外键+JOIN 保证一致性（**跨库做不到，这是溯源完整度的工程基础**）；③零新运维面降低 R1 风险。

**⚠️ 重要更新（2026-09-16 调研）**：
- **Kuzu 已归档（2025-10-10）**——嵌入式图库路线已死，graphiti 的 Kuzu 后端已被官方标记 deprecated。**原"graphiti-on-Kuzu 作为 PoC 备选"的降级路径作废**。
- 若 PG 多跳确实超标，现实备选是 **Apache AGE**（PG 图扩展，Apache-2.0，活跃）——但需评估其与 PG 主版本兼容性。**默认仍走 PG JSONB + CTE**。
- 新增性能优化：对 ≤3 跳预计算**传递闭包表**（或物化视图），热点路径查表 O(1)，闭包随增量更新维护。

**GraphStore 抽象**（服务层 seam，切换成本 ~3 人日）：
```python
class GraphStore(ABC):
    async def upsert_entities(self, ents) -> None: ...
    async def upsert_relations(self, rels) -> None: ...
    async def neighbors(self, entity_ids, rel_types, hop=1, valid_at=None) -> Subgraph: ...
    async def multi_hop(self, seeds, hop_plan, beam=3, depth=3, valid_at=None) -> list[Path]: ...
    async def supersede(self, edge_ids, invalid_at) -> None: ...
    async def reachable_decisions(self, entity_ids) -> list[str]: ...
```

**PoC 三必测点**（T-07 第一周，预算 0.1M token 级）：P1 多跳 p95（2万实体/depth3/beam3）<1.5s；P2 增量更新延迟（500 supersede+200 upsert）p95 <200ms/批；P3 ES 协同端到端 p95 <3s。

## 3. L3 决策执行：检索-推理双驱动（K3，★含创新点②）

### 3.1 三路定义与路由

| 路 | 适用 | 执行 | 延迟 |
|---|---|---|---|
| **检索路 R** | lookup 型（单点事实） | knowledge_base_search + kg_search（1 跳邻域）→ 组装回答+引用 | 3-8s |
| **推理路 M** | multi-hop/judgment 型 | kg_multi_hop 束搜索 → 证据链 → 决策卡 | 10-25s |
| **双路并发 RM** | 边界型 | R 与 M 并发，按证据质量融合 | 15-30s |

**路由算法（DECISION：规则前置 + LLM few-shot 分类，不做分类器训练）**：
```python
def route(question, ctx) -> Route:
    if hits(LOOKUP_RULES, question):        # 6 条规则：问句模板+实体数≤1+无比较/因果词
        return R
    if needs_version_compare(question):     # 版本敏感词（"新版指南"/"2024 vs 2020"）
        return RM
    cls = llm_classify(question, fewshot=ROUTER_EXAMPLES)   # 小模型，~200 token
    if cls.conf < 0.7: return RM            # 不确定 → 默认双路（宁可慢不可错）
    return cls.route                        # 第三层：历史通过率修正
```
不做分类器训练（需标注数据，违背低资源叙事）。

### 3.2 ★创新点②：版本钉住的多跳推理（文献空白 B2）

**现状问题**：决策卡只有 `knowledge_stamp`（版本戳）作为**标注**，没有算法真正把多跳遍历约束到该版本。

**形式化定义（可直接写进文档）**：
```
定义（版本钉住路径）：给定知识版本 v（本体版本 + 事实有效时间截止 t_v），
一条多跳路径 p = (e₀, r₁, e₁, r₂, ..., eₖ) 在版本 v 下"有效"，
当且仅当 ∀i: valid_at(rᵢ) ≤ t_v 且 (invalid_at(rᵢ) IS NULL OR invalid_at(rᵢ) > t_v)。

定义（版本钉住查询）：Q_v = 在仅由版本 v 有效事实构成的子图 G_v 上求答案。
```

**算法**：在束搜索的每次 `expand` 邻域查询中，**强制附加版本谓词**（`valid_at ≤ t_v AND (invalid_at IS NULL OR invalid_at > t_v)`），使每跳都在 G_v 内。实现上是 SQL 递归 CTE 加一个时间谓词——**成本极低，语义上是新的**。

**为什么这是创新**：`Temporal Validity in Retrieval Memory`（2606.26511）刚证明**余弦相似度几乎无法区分过期事实（AUROC 0.59）**——即"用普通检索回答版本敏感问题"结构上就是错的。本方案用**图上的版本约束遍历**正面解决，且**文献检索无先例**。

**束搜索主体**：
```python
async def multi_hop(question, version, depth_limit=3, beam=3) -> EvidenceChain:
    hop_plans = [await plan_hops(question)]
    paths = [Path(frontier=[seed_entities(question)], depth=0)]
    for depth in range(depth_limit):
        candidates = []
        for p in paths:
            next_hops = await expand(p, beam, version)   # ★版本谓词在此生效
            candidates += [p.extend(h) for h in next_hops]
        scored = [(c, await score_path(c, question)) for c in candidates]  # 批量打分
        paths = top_k(scored, beam)
        if any(path_answers(paths)): break
    return assemble_chain(paths)
```
- **跳数标定**：T-09 在 30 个多跳题上跑 depth ∈ {1,2,3,4} 网格，记录"准确率-token-延迟"三轴（预期 depth=3 收益饱和）。
- **PPR（HippoRAG 思想）**：作为 expand 环节的候选排序器备选（首版用 embedding 相似度+关系类型白名单）。
- **性能**：路径级缓存（相同 frontier/depth/version 命中复用）+ 类型化路径约束（关系类型白名单先剪枝）+ 打分批量化。

**消融（必须做）**：版本钉住 on/off，在 V 题（20 题版本敏感）上对比——预期 on 版本下 V 题正确率显著上升、且**不误翻 F 题**（F 题回归护栏）。**这组数字就是"可进化"的最硬证据**。

## 4. L4 知识进化：标准对齐器（K5，★创新点①，创新主轴）

### 4.1 文档变更检测（三段式）

```
输入: 指南 v_old, v_new（均已在 doc_asset_t 登记, supersede_of 链接）
STEP 1 章节树对齐（确定性）: 章节标题归一化（编号剥离+同义词折叠）→ 树编辑距离对齐（DP）
     输出: {matched / added / deleted / moved / renumbered}
STEP 2 段落语义对齐（仅 matched 章节）: 段落 embedding 相似度矩阵 → 匈牙利算法最优配对
     相似 ≥0.85 → 进入 STEP 3；0.6-0.85 → LLM 裁决（中档，~300 token/对）
STEP 3 变更分类（每对齐段落）:
     sim ≥0.98 → UNCHANGED（跳过）；否则 LLM 分类 → {ADD/UPDATE/DELETE/MOVE/RENUMBER/SPLIT/MERGE}
     + 抽取变更要点（命题级 diff）
```
**查准/查全目标**：P≥0.90 / R≥0.85（从机器输出抽 60 个变更判定人工核对）。R 低可接受（漏检以 `source_stale` 兜底，不静默错）；P 低才浪费专家时间。

**表格型标准变更**：药品剂量表/检验参考区间表用**确定性 diff**（行列 hash 比对）——零 LLM、可复现。

### 4.2 受影响面分析（变更 → 图谱 → 决策传播）

```
输入: 变更段落集合 ΔS
1. 图谱锚定: evidence_span ∈ ΔS 的全部 kg_evidence_t → 受影响实体/关系集 E_aff
2. 反向传播: decision_card_t.evidence_chain 的 kg_path 引用 E_aff 的决策卡集 D_aff
   （预计算倒排：决策卡生成时维护 entity → [decision_card_id]，GIN 索引直接服务）
3. 输出影响报告: {E_aff 清单, D_aff 清单（含原结论）, 建议动作}
```
**DECISION：轻量预计算**（不做在线图遍历）——受影响面查询 = 两次索引查询，O(1) 更新。规模上限：决策卡 1 万张、实体 2 万时索引查询 <100ms（E，PoC 验证）。

### 4.3 ★创新内核：最小充分更新集（minimal sufficient update set）

原 K5 是工程流程，缺"优化"内核。新增：

```
输入：变更段落集 ΔS、受影响实体集 E_aff、受影响决策卡集 D_aff、受影响本体提案集 P_aff
目标：选择最小的人工确认/重算集合 U ⊆ (P_aff ∪ D_aff)，
      使"未纳入 U 的项保持旧结论"带来的质量损失 ≤ 阈值 ε。
方法：对每项估 value-of-information = P(结论会因变更而改变) × impact(该结论被引用次数)，
      按 VOI 降序贪心选入 U，直到边际收益 < 成本。
```

**这同时解决了 §2.1 的人审预算问题**（同一个 VOI 框架）——**一次设计，两处空白**（E1 + A2）。

**"演进成本 vs 重建成本"形式化**：`成本节省率 = 1 - (增量演进的 token+人时)/(全量重建的 token+人时)`，并报告**质量保持率**（演进后分数 / 重建后分数）——直接回应"为什么不每次重建知识库"。

### 4.4 重算队列与更新提案

- **事实级**：E_aff 的旧事实按 §2.4 受控失效打戳，新事实抽取入图；
- **本体级**：变更要点若映射为"新类/改属性/新关系"（LLM 判断）→ 生成 K1 增量提案（复用同一确认-版本化通道，`trigger_source=standard_update`）；
- **决策级**：D_aff 卡标 `needs_rerun=true` + 重算（问答时自动用新知识戳重出卡，或批处理重跑入 `evolution_round_t`）；重算前后结论对比自动记录。

## 6. 评测体系（K4 + A5）

### 6.1 决策测试集（120 题）

| 题型 | 数量 | 测什么 | 出题方式 |
|---|---|---|---|
| 事实型 F | 35 | 基础检索召回 | 从语料直接出题 |
| 多跳型 M | 45 | 跨文档推理 | SOP 决策问题 LLM 扩展 → 人工校验 |
| 版本敏感型 V | 20 | 知识进化 | 从 2020 vs 2024 diff 条目出题（与 K5 共建） |
| 拒绝回答型 X | 20 | 知识边界自知 | 半数故意问语料外问题 |

**V 题双标签**：每题带 `answer_old`/`answer_new`，分别在旧版/新版知识戳下评测——Q2 数字直接由 V 题差值产生。

**构建协议**：种子（SOP 30 题）→ LLM 扩展（每种子 2-3 变体，候选池 ~200）→ 人工校验（3 队员交叉标注，Krippendorff α ≥0.7）→ 120 题入库（冗余 ~1.7 倍）→ hash 固化。
**防过拟合隔离**：测试集文档来源与本体构建语料隔离（80% 构建 / 20% 评测盲区），M/F 题至少 50% 证据来自盲区文档。

### 6.2 指标

| 指标 | 定义 | 实现 |
|---|---|---|
| 准确率 Acc | LLM-as-judge rubric + 拒答题确定性规则 | 原生 LLM 评测器（五元组 rubric） |
| **pass^2** | 每题跑 3 次，≥2 次判对的题占比（主指标）；pass^3 并报 | 自研 code 评测器 + `eval_run_t` 聚合 |
| 溯源完整度 Trace | 证据链字段完整率 × 抽查人工验证率 | code 评测器（读 `runtime_events`） |
| 延迟/成本 | p95 延迟、token/题 | cost-ledger 自动采集 |

**样本量（诚实口径）**：单轮 120 题不足统计功效（检出 5pp 需 ~376 题）；**DECISION：以 3 次重复的 pass^2 口径报告**（120×3=360 观测），将"检出 5pp"降格为"检出 ≥8pp"+报告 95% CI。答辩话术："报告置信区间与效应量，不宣称 5pp 显著"。

### 6.3 LLM-as-judge 偏差控制

1. **judge 分离**：judge 用大档且与生成不同家族（生成 Qwen→judge GLM，反之亦然），同模型自评禁止。
2. **Rubric 数学化**：五元组核对 `{关键事实项(0.6), 拒答判定, 证据引用存在性, 推理步骤完备性, 安全边界}`，每项 0/1 加权，总分 ≥0.8 判对；五元组题入库时写死。
3. **翻转测试**：20% 题候选答案顺序翻转重判，位置一致性 ≥95%；长度-判分相关系数 >0.3 视为长度偏差警告。
4. **人工抽检 10%**：judge-人工一致率 ≥90% 达标。

### 6.4 知识进化评测（Q2）与迁移评测（Q4）

```
Round_v1: 知识=指南2020版 → 全测试集（V 题 answer_old 口径）→ Acc₁/Trace₁
演进事件: 摄入2024版 → K5 变更检测→受影响面→提案→确认→增量演进（全流程记账）
Round_v2: 知识=指南2024版 → 同测试集（V 题 answer_new 口径）→ Acc₂/Trace₂
报告: ΔV题正确率（预期 +15pp 以上, E）、全量 Acc 变化、演进成本 vs 重建成本
```
**迁移评测**（附加分）：迁移人日 ≤10、迁移 token ≤1.5M、本体规模 30-80%、**参数复用率 ≥70%**（"轻量化"的量化口径）、政务域 30 题 pass^2 ≥ 医疗的 90%。

### 6.5 与 Nexent 评估工作台对接（A5：零侵入）

**DECISION（源码核验后的更优解）**：评估工作台的 code 型评测器是**带沙箱与白名单的 Python 代码评测器**，签名固定：

- `knowevo_passk`/`knowevo_trace` 写成 **code 评测器**（纯 Python，注册界面导入 json，**零上游改动**）；
- `knowevo_judge`（LLM rubric 五元组）用工作台**原生 LLM 评测器**配置实现；
- **`runtime_events` 参数能拿到智能体运行时事件流**（含工具调用记录）——正是溯源完整度指标需要的原料；
- **上游 `evaluator_service.py` 一个字符都不用改**。理由：零侵入 > 扩展点改造（上游月度同步零冲突），评分维度1"深度集成"叙事更强。
- ⚠️ 注意：上游 v2.5.1 后行号漂移，`evaluate()` 调用点从文档所述的 986-1030 变为 ~920-956（因上游新增 `runtime_events`/`conversation_history` 参数）。引用时以实际源码为准。
