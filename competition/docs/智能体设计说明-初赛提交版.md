## ① 智能体定位与总体架构

**定位**：以 2 型糖尿病用药决策为主场景的**领域知识资产认知与决策智能体**，构建于华为 ModelEngine Nexent 平台（v2.6.0）。它把沉睡的行业文档（指南 / 说明书 / 临床路径 / 检验单）激活为**版本化的知识图谱资产**，通过「检索-推理」双驱动执行流产出**每一步可溯源的用药决策卡**，并让知识体系随行业标准演进而**增量进化**。

**总体架构（六层，自顶向下）**：

```
L5 交互层   本体工作台(树/diff/版本) · 决策卡面板(证据链展开) · 模板库页 · 评测报告
L4 知识进化层 ★创新主轴
            标准对齐器：变更检测 → 受影响面 → 最小充分更新集
            冲突消解 · Skill 模板库（轨迹→模式→SKILL.md）
L3 决策执行层
            检索-推理双驱动：路由(规则+few-shot)
              检索路(knowledge_base_search + kg_search) ／
              推理路(kg_multi_hop 束搜索·版本钉住★) → 证据链融合 → 决策卡
L2 知识引擎层
            本体半自动构建(种子引导 + 两级提案 + 人审预算★) · 本体锚定抽取 · 三级实体对齐 · bi-temporal · PG JSONB+递归CTE图存储
L1 数据资产层
            Nexent 摄取管线(Unstructured) + 专项解析兜底 · registry 资产登记（编号/模态/权威等级/出版日/血缘）
L0 Nexent 底座 v2.6.0（fork·零修改）
            FastAPI 多服务 + Next.js 15 + PG/ES/Redis/MinIO + smolagents 内核 + MCP 生态 + SKILL.md 渐进披露 + 三层记忆&Dreaming + 智能体评估 + RBAC
```

**设计铁律**（A：代码结构实证）：① 最小侵入上游——业务代码全部在自包含目录（`backend/services/knowevo/`、`mcp_servers/knowevo_mcp/`、`frontend/features/*`），上游 Nexent 零修改（除 ≤30 行纯新增渲染分支），v2.5.0→v2.6.0 实测零冲突合并；② 弃用优先于删除——知识资产只打戳不物理删除，决策卡历史可回溯；③ 零侵入评测——自定义指标写成 Nexent 原生 Code 判定，签名逐字 `evaluate(query, expected, actual, runtime_events)`，上游评估服务零改动。

> ⚠️ **已知弱项（如实声明，不掩盖）**：L5 资产看板与进化看板动画**未实现**（资产看板经裁决放弃，见 `00-总纲与决策依据.md` §九）；「多模态」以文本/表格/图文首版为主，缺量化实验；跨文档规模证据受图谱摄取进度限制（详见 ④）。

## ③ 工具面（自研 5 个 KG MCP 工具 + 平台工具）

### 3.1 自研 KnowEvo MCP 工具（双注册，代码层）

> **对外唯一口径：已注册 5 个**（`backend/tool_collection/mcp/kg_tools.py:53-55` 的 `KG_MCP_TOOL_NAMES`）。历史上「8 个」指 `knowevo/mcp_servers/knowevo_mcp/SPEC.md` 的**规划词表**，与「实际注册数」不可混用。

| 工具名 | 功能 | 输入（要点） | 输出 | 对应任务 |
|---|---|---|---|---|
| `kg_search` | 图谱实体/邻域检索（1 跳） | 查询词、hop(1–2)、top_k(1–20) | 实体+关系+证据 | T-07b |
| `kg_stats` | 图谱统计 | 统计维度(graph/full) | 实体/关系/类别计数 | T-07b |
| `kg_multi_hop` | 版本钉住多跳 + 证据链 | 起点实体、跳数(1–3)、beam(1–3)、版本语义 | PathSet + evidence_chain | T-09 |
| `decision_card_render` | 决策卡结构化输出 | EvidenceBundle、约束、mode(full/lite) | 决策卡 JSON（版本戳/置信度/免责） | T-19 |
| `skill_template_apply` | 模板实例化 | 领域、任务类型、关系模板、规则 | 实例化 Skill 模板（四变量） | T-20 |

**双注册机制（单 schema 源、无漂移）**：同一份 Pydantic schema（`mcp_servers/knowevo_mcp/schemas.py`）→ 同一份 handler（`server.py`）→ 导出到两个注册面：① 独立 FastMCP SSE 服务（`server.py` 的 `mcp` 实例）；② 平台内置 Local MCP（`kg_tools.py` 把同一个 `mcp` 实例 `mount` 进 `local_mcp_service.py`）。两个面共用同一应用实例，故每个工具名全平台唯一、不会漂移。复现命令见 `docs/mcp-file-guide.md` §9（已实跑：工具数=5、两注册面集合相等=True、5 个 `@mcp.tool` 注册点）。

**关键设计（避免误读）**：`kg_multi_hop` 的 `version_valid=False` 路径**不被隐藏**，而是放进 `failed` 返回——调用方需看到「证据被拒绝」及原因；消融实验依赖两个变体都可观测。`decision_card_render` 无证据时以 `INSUFFICIENT_EVIDENCE` **诚实拒绝**（真实问答截图三轮均触发此路径，见 ⑥）。

## ⑤ 调用关系与双驱动决策链路

**总体调用关系图**（完整 Mermaid 版见 `docs/call-graph.md`）：

```
用户提问
  → Agent 主进程（duty prompt 只写职责与约束）
  → 入口 Skill: domain-asset-cognition（路由）
       ├─ 单点事实类（检索路）→ Skill retrieval-path
       │      → kg_search ／ 平台 knowledge_base_search（ES 混合检索）
       └─ 多跳/演进类（推理路）→ Skill reasoning-path
              → kg_multi_hop（束搜索 · 版本钉住★）
  → Skill evidence-assembly → decision_card_render
  → 决策卡落库 decision_card_t 并展示（含知识版本戳 + 证据链 + 免责声明）

旁路：本体/版本管理 → ontology_service.commit_version → ontology_version_t
存储：PostgreSQL JSONB（kg_graph / kg_evidence_t / decision_card_t / skill_template_t / eval_run_t）；Elasticsearch（知识库文档索引）
评测：平台「智能体评估」Code 判定 evaluate(query, expected, actual, runtime_events) → eval_run_t → 消融报告
```

**双驱动决策链路逐条拆解**：

1. **检索-推理双驱动问答**（示例问答截图对应路径）：用户提问 → Agent（duty prompt 只定职责与约束）→ 入口 Skill `domain-asset-cognition`（路由）→ 单点事实类走 `kg_search`/`knowledge_base_search`、多跳/演进类走 `kg_multi_hop`（版本钉住 + 证据链）→ 证据装配 `evidence-assembly` → `decision_card_render` → 决策卡写 `decision_card_t` 并展示。**可回溯性**：`decision_card_t` 行按 `created_at` 倒序可查（T-23 验收 psql 命令）。
2. **知识图谱变更 → 增量演进**（「可进化」核心路径）：新文档 → 摄取管线+专项解析 → `ingest_graph`（LLM 抽取 entities/edges，props 带 `doc_id` 证据链）→ `PgJsonbGraphStore` 写 `kg_graph`/`kg_evidence_t` → `ontology_service.commit_version` 发布本体新版本 → `version_pin` 版本钉住（旧版保留，多跳按版本语义取数）→ `skill_template_apply` 复用模板实例化新资产。
3. **评测闭环**（「可进化」实据之一，零侵入）：评测集 → 平台「智能体评估」Code 判定 → `eval_run_t` 落库 → `e2-ablation-report.json`（消融矩阵）→ 回填决策卡/演进台账。

> **「可进化」口径澄清**：本项目的可进化能力来自 L4（标准对齐器 + 版本钉住 + 增量演进），**不是** Nexent 平台自带能力。平台侧可引的实据仅三件：Dreaming 记忆整理、Agent 版本管理回滚、智能体评估反馈闭环。

## ⑥ 调试迭代过程与示例问答

### 6.1 调试迭代经验（摘要，完整版见 `docs/pitfalls.md` 台账）

- **诚实性血泪（一）**：E1 基线曾因 eval 判定「忽略未答」污染分母——改为「未答计错」并全量重跑（诚实口径 acc=0.6667 / n_judged=60/60，旧口径 0.7692 作废）。
- **诚实性血泪（二）**：E8 版本钉住消融曾出现跨 invocation 伪 Δ=+0.3334，经同一次 invocation 配对复跑纠正为 **Δ=0.0（honest null）**（详见 `pitfalls.md` #62）——教训「不同批次两臂不能当配对实验」。
- **LLM 契约坑**：平台 llm 契约要求返回解析后 dict；`str` 返回会在 `_parse_extraction` 被拆字符炸掉——摄取驱动补了 str→JSON 适配层（仓库零改动）。
- **网关契约坑**：sensenova 网关要求 `reasoning_effort:none` 必须与 `thinking:disabled` 成对下发，否则 400（`pitfalls.md` #60）。
- **429 风暴**：网关 tpm 小配额，连续打 1-2 span 即撞 429——驱动内置风暴熔断 + 断点续跑（span_hash 幂等），空段绝不写死。
- **双注册一致性**：Local MCP 与 FastMCP 共享单 schema（`tool_schemas()`/`handlers()`），保证工具名全平台唯一。

## ⑦ 跨域可迁移性（结构性论述，非实测）

> **本节定位**：官方评分维度①明文要求「适配**多行业场景**迭代需求」、维度②点名「医疗、金融、制造、政务真实行业痛点」。本节**只做结构性论述与可迁移性的代码证据化**；**多行业实测由任务Q4 补，本稿只作结构性论述，绝不把没跑的迁移写成「已验证」**。语料 58 份**全在糖尿病域**——这一点如实声明，不掩盖。

**迁移的入口证据（代码结构层面，非运行实测）**：

1. **`corpus/registry.csv` 是唯一人工可编辑入口**：10 列契约（`asset_no/title/doc_type/modality/authority_level/source_url/license_note/local_file/split/published_at`）与具体行业无关；换行业 = 换 `registry.csv` 登记 + 换语料原件，无需改摄取/抽取代码。
2. **无硬编码域名词**：图谱实体类别（`kg_entity_t`）来自本体 v1.1.0 的 10 类 / 10 关系（可配置），`doc_asset_t` 的字段（`asset_no`/`authority_level`/`published_at`/血缘）**域无关**；抽取约束走「子图检索注入 fewshot」而非写死词表，域词由 prompt 与本体驱动。
3. **迁移脚本化**：`pipeline/ingest_assets.py`（登记→血缘→原生链）+ `pipeline/diff_guidelines.py`（标准演进对齐器）均为通用管线，行业差异收敛到 `registry.csv` 与域词表两层，不触碰 `backend/services/knowevo/` 核心实现。

**结论（诚实）**：从代码结构看，本项目满足「换 `corpus/registry.csv` + 换迁移脚本/域词表即可换域」的配置化迁移前提；**但换域后的本体质量、实体/关系产出、迁移单位成本等均属 `insufficient_data`——待任务Q4 在政务/制造（或金融/政务）域做轻量迁移实测后，方有真数字可填**（该实测同时喂养初赛维度①②与决赛附加分①）。
